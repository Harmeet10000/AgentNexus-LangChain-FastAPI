# ADR: `documents` / `chunks` is the sole retrieval schema

## Status

**Accepted** — 2026-08-17.

This ADR is deliberately accepted **ahead of its own change's code**, because change 1 implements persistence
nodes before change 2's code lands. Change 1 builds against this contract; it does not need to read change 2's
plan, and it must not wait for change 2's implementation. The single ordering exception in the refactor's work
order exists for this document.

## Context

The repository contains five candidate document schemas — `documents`/`chunks`, `search_documents`/`search_chunks`,
`clauses`, `parent_documents`, and `document_vectors` — and a promoted ingestion pipeline whose persistence nodes
write the third and fourth of them. A live probe of the actual database established that **none of these tables
exists**: the migration lineage is stamped past the entire document branch while only the billing tables were ever
created. So there are not five parallel schemas in production; there are zero, and no data anywhere depends on any
of them.

That makes this a free choice, made once, at the cheapest possible moment — before the first row is written. It
also makes it urgent: without a recorded contract, change 1 would build a promoted pipeline writing a schema
change 2 then abolishes, and change 2 would grow a clause-to-chunk migration for zero rows.

## Decision

**`documents` and `chunks` are the sole retrieval truth. `clauses`, `search_documents`, `search_chunks`,
`parent_documents`, `statutes` and `document_vectors` are not retrieval tables, and none of them is created.**
`clause` is not a table: it is a `chunk_kind` value on a chunk row, with the clause's own label in
`chunks.clause_type`. All document retrieval — keyword, vector, fuzzy, their rank fusion, and any graph-backed
path above them — reads from these two tables and no others.

### Table identity

Exactly two tables, named `documents` and `chunks`, in the application's primary PostgreSQL database. One row per
document; one row per chunk; `chunks.document_id` references `documents.id` with `ON DELETE CASCADE`, so a chunk
never outlives its document.

### Required fields a writer must supply

**`documents`** — a writer MUST supply all five of:

| Field | Type | Contract |
|---|---|---|
| `id` | uuid, NOT NULL, primary key, **no database default** | **Generated by the writer.** The ORM supplies it from a Python-side `uuid4` default, which fires only for ORM-mapped inserts. A writer issuing raw SQL MUST generate and pass it explicitly; there is no `DEFAULT gen_random_uuid()` to fall back on. |
| `user_id` | varchar(255), **NOT NULL, no default** | The authenticated owner. Never a sentinel, never a shared value, never empty, never supplied by the database. |
| `title` | varchar(500), NOT NULL | Human-readable document title. |
| `object_uri` | text, **NOT NULL, no default** | Reference to the immutable stored source object. It is the provenance link that makes re-parsing after a chunker change possible; an empty value means the text came from nowhere. |
| `content_hash` | varchar(64), NOT NULL | Digest of the document content. Half of the identity key below. |

Everything else on `documents` is nullable or defaulted: `source_uri` (nullable), `document_kind` (defaults
`'generic'`), `status` (defaults `'received'`), `jurisdiction`, `contract_type` (both nullable), `parties`
(defaults `[]`), `metadata_` (defaults `{}`), `created_at` and `updated_at` (both NOT NULL, defaulted to now,
`updated_at` advancing on update).

**`chunks`** — a writer MUST supply all six of:

| Field | Type | Contract |
|---|---|---|
| `id` | uuid, NOT NULL, primary key, **no database default** | **Generated by the writer**, on the same terms as `documents.id` above. Raw-SQL inserts are the expected chunk-write path, and the ORM's `uuid4` default does not fire for them. |
| `document_id` | uuid, NOT NULL | Parent document. |
| `user_id` | varchar(255), **NOT NULL, no default** | The same owner as the parent document. Every retrieval predicate is scoped by it. |
| `chunk_index` | integer, NOT NULL | Position within the document; unique per document. |
| `content` | text, NOT NULL | The chunk text. |
| `updated_at` | timestamptz, **NOT NULL** | Must be written **on every write, including a conflict-resolving upsert**. See the trap below. |

Nullable or defaulted: `chunk_kind` (defaults `'generic'`; this is where `clause` lives), `preamble` (defaults
`''`), `clause_type` (nullable), `page_no` (defaults `0`), `embedding` (**nullable** — a chunk may legitimately
exist before it is embedded), `metadata_` and `custom_metadata` (default `{}`), `quality_warnings` (defaults
`[]`), `graphiti_episode_id` (nullable), `graphiti_verified` (defaults false), `created_at`, and the three statute
identity attributes below (all nullable).

### Statute identity attributes live on the chunk row

**A statutory provision is a chunk, not a table.** The never-created `statutes` table is not resurrected; instead
`chunks` carries three nullable attributes that make a provision addressable, and one index that makes the lookup
cheap:

| Field | Type | Contract |
|---|---|---|
| `instrument_name` | varchar(255), NULL | The instrument the provision belongs to, in a **normalized** form the ingestion path controls — deliberately *not* the parent document's free-text `title`, because identity that piggybacks on a display string drifts the first time a title is reformatted. |
| `section_ref` | varchar(64), NULL | The provision reference within that instrument, stored as authored (`12`, `12A`, `12(3)`). Not parsed into parts; a point lookup compares it whole. |
| `instrument_year` | smallint, NULL | The year of the instrument edition this provision is drawn from. It is the discriminator when the same section is held at more than one vintage. |

All three are NULL for the corpus's non-statute majority, and a writer that supplies one SHALL supply
`instrument_name` and `section_ref` together — a section reference with no instrument is not addressable.

**The index, and why its column order is the whole design.**
`ix_chunks_instrument_section` on `(user_id, instrument_name, section_ref, instrument_year)`, partial,
`WHERE instrument_name IS NOT NULL`.

- `user_id` leads because every retrieval predicate in this schema is tenant-scoped; an index that did not lead with
  it would not be usable by any read this contract permits.
- Equality on the first three columns is the point lookup, so addressing a provision by instrument and section is
  one index descent rather than a scan of the corpus.
- `instrument_year` trails so the matching rows arrive **already ordered by vintage**. A btree scans backwards at no
  cost, so *newest applicable year wins* is the first row of a backward scan — no sort, no aggregate, no
  self-join.
- The index is **partial** so the non-statute majority of chunks pays neither storage nor write amplification on the
  hottest table in the schema.

**Newest applicable year wins, stated so two readers implement it identically.** When more than one chunk matches
`(user_id, instrument_name, section_ref)`, the winner is the row with the **greatest `instrument_year` not exceeding
the caller's as-of year**; with no as-of year supplied, the greatest `instrument_year` outright. A row with a NULL
`instrument_year` loses to any row that has one, and wins only if it is the sole match. If two rows still tie on
year, the most recently written row wins (`updated_at`) — and a tie is a corpus-quality signal worth logging, not a
retrieval decision worth tuning.

`chunks.search_text` is **generated by the database and MUST NOT be supplied by a writer**. It is a stored
generated column concatenating `clause_type`, `preamble` and `content`, and it is the column all three retrieval
branches match against.

**Both directions on the primary key, stated together so neither is guessed.** `id` on both tables MUST be
supplied by the writer; `search_text` MUST NOT. Neither table carries a database default for `id`, so a writer
that omits it gets a NOT NULL violation on its first insert rather than a generated key. If a
`DEFAULT gen_random_uuid()` is preferred, that is a change-0 DDL input and must be added to the column tables in
`design.md` before change 0 authors the migration — it is not a decision a writer may assume.

**The `updated_at` trap, stated because missing it produces the worst outcome.** The ORM's update hook fires for
update statements but **not** for an insert that resolves a uniqueness conflict into an update — which is the only
way chunks are written. The value must therefore appear both in the row payload the ingest path builds *and* in
the conflict-resolution set. Miss either and the column exists, is non-nullable, and never changes: it looks
maintained and is not.

### Identity and dedup keys

- **Document identity is the pair `(user_id, content_hash)`**, enforced by unique constraint
  `uq_documents_user_content_hash`. **Not the digest alone.** Byte-identical content owned by two tenants is two
  documents with two chunk sets. Re-ingesting content the same tenant already owns reuses that document. A writer
  resolving a document conflict names **that** constraint: there is no `doc_id` column on `documents` to conflict
  on, so a conflict target carried over from a superseded schema fails at parse time, not at review time.
- **Chunk upsert key is `(document_id, chunk_index)`**, enforced by unique constraint
  `uq_chunks_document_chunk_index`. Writers resolving conflicts must name **that** constraint. The name is
  load-bearing and is asserted by a static gate.
- The keyword index name `chunks_bm25_idx` is likewise load-bearing, and more strongly than "load-bearing" usually
  means: it is not a convention but a **literal argument in the query**. The keyword-search function is overloaded
  as `to_bm25query(input_text text)` and `to_bm25query(input_text text, index_name text)`, and every retrieval query
  uses the two-argument, index-scoped form because the function reads that index's corpus statistics. So an index
  with a **correct definition under a different name does not satisfy the query** — it silently matches nothing
  rather than failing to build. Renaming it is a runtime break with no lint, type or migration warning, which is why
  it is asserted by a static gate. The access method is `bm25` and the default operator class on a `text` column is
  `text_bm25_ops`; both are confirmed present on the live server, though **no `bm25` index exists there yet** —
  confirming the access method is not confirming the index.

### Explicitly NOT part of this contract

- **The parsed document text.** `documents` stores **no full-text body column** — there is no `markdown`, no
  `content`, no `raw_text`. `object_uri` is the provenance link, and parsed text is **re-derived** from the stored
  immutable object whenever it is needed; that is the whole reason the reference is required and non-nullable. A
  writer migrating off a schema that carried a parsed-text column drops that column rather than relocating it, and
  in particular **does not** move a document body into `metadata_`. The chunk rows carry the only text this schema
  persists.
- **Derived per-document summaries and session scope.** A document-level summary and any thread, session or
  conversation identifier belong in `documents.metadata_`, as scalars under stable keys. `metadata_` is for scalars
  and small structures that a query may filter on — it is **never** a home for a document body, and the GIN index
  over it makes that distinction load-bearing rather than stylistic. A writer whose prior schema had `summary` and
  `thread_id` columns puts both in `metadata_`; a writer that instead needs to *retrieve* by summary text chunks it
  like any other text.
- **Any DDL.** Change 2 authors no migration. Change 0's single create-schema migration is authoritative for
  these two tables, including the new chunk `updated_at` column and the three retrieval indexes.
- **A third table for document hierarchy.** Structure is carried on the chunk row — `chunk_kind`, `clause_type`,
  `preamble`, `page_no`, `instrument_name`, `section_ref`, `instrument_year`, `metadata_`, `custom_metadata` — and
  by the document-to-chunk foreign key. This is also the answer for statutes specifically: **no `statutes` table**,
  because a provision is a chunk with those three attributes set. If a parent/child chunk hierarchy beyond that
  proves necessary, it must **supersede this ADR**, not arrive as a fourth table alongside it.
- **The knowledge-graph store.** Entities, relationships and episodes live in the graph system, not in these two
  tables; `chunks.graphiti_episode_id` and `chunks.graphiti_verified` are the only link, and they are optional.
  That role boundary is a separate ADR, owned by the memory change.
- **Embedding decisions.** The vector dimension's value and whether stored vectors are normalized are not fixed
  here. The dimension must come from the single configured source rather than a literal, and the normalization
  convention must be chosen before the first row is written — both owned by change 1.
- **Retrieval quality.** The fuzzy-similarity floor, the rank-fusion constant, re-ranking, and whether the
  graph-backed or hand-rolled question-answering path survives are all change 1's. This contract fixes *where*
  retrieval reads, not *how well* it ranks.
- **Reachability and authorization.** Which endpoints are mounted and how the owner is resolved from a request are
  change 0's. This contract requires that an owner exist; it does not specify how it is authenticated.
- **Any claim that retrieval works today.** None of the three retrieval indexes has ever been created in any
  environment, and the fuzzy-match extension is not installed. The target schema *defines* the equivalents; it has
  never run them.

## Rationale / Alternatives

`documents`/`chunks` wins on merits, not merely by being the newest:

- It is the only candidate with an **owner column**, so it is the only one that can express tenant isolation or
  per-tenant identity at all. The superseded search table has no owner column, so it could not have done better.
- Its retrieval surface is already a **superset** of the alternative's: the same three branches plus owner,
  document, clause-type and verification filters — and it already names the correct uniqueness constraint.
- Its searchable text is derived by the database from the chunk's own fields, so it cannot drift from them, and it
  carries clause and preamble context into every branch's matching.

**Alternative A — keep the search tables as the retrieval truth.** Rejected: no owner column, global digest
deduplication that leaks across tenants, a second derived text-search column with **zero readers**, and a
uniqueness constraint that no migration ever created.

**Alternative B — keep `clauses` as the legal-retrieval truth alongside `chunks`.** Rejected: no migration creates
that table, its keyword index is declared on a table created nowhere, and the live database confirms it has never
existed. Preserving it would mean preserving readers of a table nothing has ever created.

**Alternative C — let change 1 write `clauses` first and migrate to `chunks` afterwards.** Rejected: it would
preserve nothing, because there are zero rows, while roughly doubling change 2 into a data migration. This is
precisely why the ADR is accepted before change 1's code rather than after.

**Alternative D — content-addressed storage: one immutable blob and chunk set keyed by digest, with per-tenant
pointer rows.** The right long-term answer to the duplication cost below, and deliberately not adopted now: it
changes the read path for every consumer. The object reference already provides content-addressed keys, so the
groundwork exists whenever it is wanted.

## Consequences

**Accepted costs.**

- **Cross-tenant duplicate storage becomes the normal case.** Two tenants holding the same public statute means two
  documents, two chunk sets, two embedding sets. Storage and embedding spend scale with tenants times shared
  documents. This is taken deliberately: global deduplication would return the first uploader's document
  identifier to the second, attribute the first uploader's metadata to both, and let one tenant's erasure destroy
  another's document.
- **Fuzzy matching is diluted by the derived text.** Character-similarity is a normalized ratio over the whole
  string, and the derived column prepends clause type and preamble to the content. A long preamble therefore
  *lowers* the similarity of a match located in the content, making the similarity floor effectively stricter for
  such chunks. Because rank fusion uses only rank position, the visible effect is branch **recall**, not score.
  Calibrating that floor is a first-time calibration in change 1, not a re-tune here.
- **The migration lineage permanently reads as a lie.** Three revisions stay stamped while creating nothing,
  because editing them is rejected and a no-op drop revision is not worth a permanent lineage node. A consequence
  of this is that rendering the full migration history offline still emits the superseded tables' `CREATE TABLE`
  statements; the guards are that no source outside frozen migration history names those tables, and that the
  authoritative create-schema migration creates neither.
- **The repository loses raw-text ingest.** The only path that accepted a title and a body of text — rather than an
  uploaded file — is deleted rather than retargeted, because it could supply neither an owner nor a stored object
  reference. No user loses anything, since it was never mounted. Restoring it means an authenticated text-ingest
  endpoint that writes a real owner and stores the raw text as an immutable object first.

**Benefits realised.**

- Change 1 can implement its persistence nodes immediately against a fixed contract, writing `chunks` from the
  start and never touching `clauses`.
- Change 3's retargeting of tools off nonexistent tables has a named destination.
- The two load-bearing identifier names are recorded, and a static gate now fails when query text names a database
  identifier no migration creates — the defect class that produced the clause-index hole in the first place.
