What NOT to Test

≈10 minutes · Prerequisites: L1–L6 · Next: Senior Anti-Patterns (lesson 8)

Beginners ask "how do I test more?" Seniors ask "what does each test buy me?" Every test costs three times: once to write, forever to maintain, and on every CI run until deleted. Testing the wrong things spends that budget while adding zero protection.

The economics of a test

A test earns its keep when the cost of writing and maintaining it is lower than the expected cost of the defects it prevents.— distilling Khorikov's value/cost framing, Unit Testing, ch. 1–2 (R1)

This single equation generates every rule below. Nothing here is dogma — it's arithmetic.

The do-not-test list

Skip testing…Why the math fails
Trivial code: one-line getters, constants, pure delegationNo logic → no realistic way to be wrong in a way tests catch. The assertion just restates the implementation
Third-party library internalsYou can't fix their bugs anyway. Test your usage: wrap the library behind your own interface and test the wrapper
Generated code & configVerified upstream or by schema validation; hand-written tests rot against regeneration
Private implementation detailsLesson 2 & 3's core trap — such tests break refactors without catching anything real
Constructors / DI wiring aloneIf nothing else, they'd fail instantly in integration tests anyway
Two senior questions before writing any test:
  1. "If this code broke, would someone notice through observable behavior?" If no — skip.
  2. "Could this code realistically break in a way this test catches?" Trivial code fails this question.

The coverage-theater warning

Chasing these exclusions feels wrong to beginners because coverage numbers drop. Resist the feeling:

  • Coverage measures execution, not verification. Code touched by weak assertions counts the same as code guarded by sharp ones.
  • Khorikov argues chasing a specific coverage target optimizes the metric instead of the goal [R1]. Teams hit "90%" and still ship regressions — the number was never the safety net.
  • Healthy use: coverage as a detector — "this risky module has 0%?" — never as a target — "everything must reach 80%".

Where restraint meets strategy

Lesson 6 taught you to read your codebase's risk. This lesson completes the loop: spend your test budget exactly there, and refuse to spend it anywhere else — including places that merely make coverage dashboards feel good. Restraint isn't laziness; it's concentration of force.
