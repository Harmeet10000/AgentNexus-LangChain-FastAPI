Test Doubles: Stubs, Mocks, Fakes

≈10 minutes · Prerequisites: L1, L2 · Next: Integration Tests (lesson 4)

Lesson 2 ended with a problem: some dependencies — databases, networks, clocks — make unit tests slow or nondeterministic. The fix is to substitute them. Those substitutes are test doubles. Used well, they're your sharpest tool. Used carelessly, they're the #1 cause of brittle suites.

Why doubles exist at all

A double stands in for a real dependency so the test controls it. You swap reality for something:

Real dependency problemWhat a double gives you
Slow (database, network)Speed — milliseconds instead of seconds
Nondeterministic (clock, random, external API)Control — fixed time, fixed responses
Stateful (needs cleanup between runs)Isolation — no shared mutable state
Hard to trigger (payment failure, outage)Reachability — error paths on demand

The last row matters more than beginners expect: without doubles, the code paths for failures — the paths that matter most in production — go untested because nobody can summon a bank outage on cue.

The taxonomy: five doubles, one family

All definitions below are from Meszaros' classic taxonomy, preserved in the glossary:

DoubleBehaviorTypical use
DummyFills a parameter; never usedSatisfying a required argument
StubReturns canned answersQueries: "what does X return?"
SpyStub + records how it was calledChecking calls after the fact
MockPre-programmed call expectationsCommands: "did we tell X to happen?"
FakeWorking lightweight implementationStateful deps: in-memory database
The one distinction that matters most: stubs answer queries (you assert on the SUT's result). Mocks verify commands (you assert on the interaction itself) — legitimate only when the interaction IS the observable outcome, like "an email got sent."

The trap: over-mocking

Here's where suites die. A beginner mocks everything, including internals:

# ❌ Brittle — tests implementation, not behavior
test "checkout":
    repo   = mock()          # internal collaborator mocked
    pricer = mock()
    expect(pricer).calculate(cart) → returns 90
    expect(repo).save(order)
    checkout(cart, repo, pricer)
    verify_all_expectations()
# ✅ Robust — asserts the outcome through public API
test "checkout returns discounted total and persists order":
    repo = FakeOrderRepository()
    total = checkout(cart, client, repo)
    assert total == 90
    assert repo.saved_order.total == 90

Both pass today. But refactor tomorrow — rename pricer.calculate, merge two internal calls into one — and the first version shatters while verifying nothing real changed. It was checking how the work got done, not that it got done.

Rule of thumbRationale
Double out-of-process deps (DB, APIs, queues)They violate speed/determinism [R1]
Don't double in-process collaborators (your own classes)You'd be testing implementation details
Never mock what you don't own (third-party internals)Your suite can't vouch for someone else's code — wrap it behind your own interface instead
Prefer fakes over mocks for stateful thingsFakes keep assertions on outcomes, not choreography
