Unit Tests: Scope and Shape

≈10 minutes · Prerequisites: Lesson 1 · Next: Test Doubles (lesson 3)

Unit tests are the foundation of every pyramid — the layer you'll write most. Get their scope wrong here and the whole suite rots. Two ideas carry this lesson: what a "unit" actually is, and the shape every unit test shares.

The unit is a behavior, not a class

Beginners define a unit test as "a test of one class or one function." That definition quietly produces terrible suites: tests get glued to internal structure, then break on every refactor.

A unit under test is a unit of behavior — an observable outcome that matters to someone using the code. It might span one function, or several classes collaborating.— Khorikov, Unit Testing, ch. 2 (R1)

Ask: "if this behavior broke, would someone notice through the public surface?" If yes, it's a unit worth testing. Private helper methods usually aren't — they're implementation details serving some public behavior that gets tested anyway.

Heuristic: test through the smallest public API that exhibits the behavior — never by reaching into privates.

Shape: Arrange–Act–Assert

Every well-formed unit test reads as three beats (pseudocode):

test "discount applies for loyal customers":
    # Arrange — build inputs and context
    cart   = Cart(items=[Item(price=100)])
    client = Client(loyal_since_years=5)

    # Act — perform exactly ONE action under test
    total = checkout_price(cart, client)

    # Assert — check ONE observable outcome
    assert total == 90
  • Act contains exactly one call. Two actions means two behaviors crammed together.
  • Assert checks one outcome. Multiple related asserts on the same result are fine; asserting five unrelated things means you wrote three tests.
  • No logic in tests: no loops, no branching, no computation. A test containing if can have its own bugs — and then who tests the test? [S-source: Google Testing Blog, Don't Put Logic in Tests]

Naming: the name IS the documentation

Name tests as claims about behavior: "applies discount when customer is loyal". When this test fails months later in CI, the failure message alone tells the team which promise was broken. Names like test_cart_2 or testCheckoutWorks throw away that value.

What disqualifies a test from being a "unit"

Recall Lesson 1's traits: fast, deterministic, independent. Anything violating them pushes a test out of the unit layer:

The code touches…Consequence
A real databaseSlow + stateful + order-dependent → integration territory
The network / another serviceSlow + nondeterministic → integration territory (with doubles)
The system clock or randomnessNondeterministic → inject time/randomness so tests control it

That third row plants a seed for Lesson 3: when a dependency makes tests slow or flaky, you don't delete the test — you substitute the dependency. Those substitutes are test doubles.
