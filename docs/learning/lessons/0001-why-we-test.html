Why We Test

≈10 minutes · Prerequisites: none · Next: Unit Tests (lesson 2)

Most beginners think testing means "checking my code works." That's backwards, and fixing this one idea changes everything about how you'll write tests.

The real job: buying confidence to change

Code that never changes doesn't really need automated tests. You could verify it once by hand and be done forever.

Real software is never finished. Requirements shift, dependencies update, teammates refactor. Every change carries the same quiet question: did I just break something?

Automated tests exist to answer that question instantly and mechanically. Their job is regression prevention — catching behavior that used to work and stopped.— The thesis of Vladimir Khorikov's Unit Testing, ch. 1 (R1)

This reframes everything. A test suite isn't proof your code is correct today. It's a machine that lets you change code tomorrow without fear. Teams with strong suites refactor aggressively; teams without them freeze, because every edit feels like defusing a bomb.

The one-sentence takeaway: you don't write tests to check code — you write them so that future changes become cheap.

Why late bugs hurt most

A bug's cost explodes the later it's found:

Found during…Cost & pain
Your own coding sessionNearly free — you fix it while context is fresh
CI / code reviewCheap — minutes of someone's attention
QA / stagingModerate — round trips, blocked releases
ProductionExpensive — customer trust, incidents, hotfixes under pressure, sometimes revenue

Tests move defect discovery leftward on this table. That leftward shift — not "quality" as an abstract virtue — is the concrete business value of testing. It's why mature companies treat their suite as infrastructure, not overhead [R4].

What separates a good test

Not all tests buy confidence. Some buy false confidence. Four traits separate the two:

TraitWhy it matters
FastYou run tests thousands of times; each wasted second compounds into a suite nobody runs
DeterministicSame code must give the same result — one flaky failure trains people to ignore red
IndependentTests share no state; any subset passes in any order
Behavior-focusedAsserts what the code does, not how it does it internally

The fourth trait is the subtlest and the source of most bad suites. We'll spend lessons 3 and 8 on it. For now: if refactoring code — changing how it works without changing what it does — breaks your tests, those tests were testing implementation, not behavior. They now block the exact activity they existed to enable.
