Senior Anti-Patterns

≈10 minutes · Prerequisites: L1–L7 · Next: Tests for Customer-Facing Products (lesson 9)

Suites rarely die from one bad decision. They die from six small habits compounding. Recognizing these by name — in code review, in your own PRs — is a large share of what "senior" means in testing.

1. Flaky tests tolerated

Lesson 5's rule bears repeating because teams violate it under pressure: flaky = broken. The corrosive habit is the auto-retry wrapper that re-runs failures until green.

Auto-retry doesn't heal flakiness — it launders it. Real nondeterminism (races, ordering, leaked state) stays in the product while the suite stops reporting it [R4]. Retry only as a temporary quarantine measure, never as policy.

Usual root causes, in frequency order: shared mutable state between tests, timing assumptions (sleep(2) instead of waiting on a condition), and uncontrolled externals (clocks, random data, live third parties).

2. Assertion roulette

A test fails and the message says assert False was not True — or there are seven bare asserts and no way to know which one tripped. Failures must be self-explaining:

# ❌ roulette — which of these failed?
assert result.total == 90
assert result.status == "pending"
assert len(result.items) == 3

# ✅ messages carry the diagnosis
assert result.total == 90, f"loyal discount wrong: got {result.total}"

This compounds with Lesson 5's diagnosability principle: every test failure should read like a bug report someone already wrote for you.

3. Mystery guest

The test's behavior depends on fixtures or state defined somewhere else entirely — a base class three files up, an external seed file, leftover database rows. You can't understand the test without an archaeology dig. Tests should be legible top-to-bottom; share machinery via helpers, but keep each test's inputs visible in its own body.

4. Logic inside tests

Recap sharpened: loops, conditionals, and string-building inside tests mean the test itself can be buggy. Google's guidance is blunt — don't put logic in tests [R4]. If a test needs branching to compute expectations, the expected values belong in explicit constants.

5. Over-DRY test code

The counterintuitive one. Production code prizes DRY (Don't Repeat Yourself); test code pays differently. Burying Arrange/Act inside five layers of clever helpers recreates Mystery Guest at scale:

Production valueTest value
No duplicationSome duplication is fine — clarity beats brevity
Abstraction hides detailThe whole test should be readable in one glance
Change once, everywhereEach test readable standalone beats global cleverness

Khorikov calls this out explicitly: refactor test code toward readability, not toward reuse [R1]. Extract only genuinely repeated, boring setup — and stop there.

6. Erasing the red

A test fails; a developer "fixes" it by deleting an assert or loosening an expectation until green — without understanding why it failed. Every silent erasure converts a safety sensor into decoration. The senior norm: a red test gets explained (real bug → fix code; outdated expectation → consciously update with justification in the commit message) before anyone touches the test file.

The pattern underneath all six

Every anti-pattern here trades long-term signal for short-term convenience: retries hide nondeterminism, erasures hide regressions, cleverness hides context. Seniors protect the suite's credibility like production uptime — because functionally, that's what it is.
