Integration Tests: Real Boundaries

≈10 minutes · Prerequisites: L1–L3 · Next: E2E Tests (lesson 5)

Your unit tests are green. The customer signs up and… the order never saves, because your ORM mapping and your schema disagree. Every component passed in isolation; the seams were never checked. Integration tests exist for the seams.

The definition that matters

An integration test verifies that multiple components work together across a real boundary: a database, a message queue, the file system, another service.— after Vocke, The Practical Test Pyramid, §Integration Tests (R2)

The dividing line from Lesson 3 sharpens here:

Ask yourself…If yes →
Does execution leave my process? (DB, network, disk)Integration test against the real thing
Is everything in-process and controllable?Unit test (double whatever's slow)
Why this layer is special: Kent C. Dodds argues integration tests give the best confidence-per-millisecond of any kind — they check that things work together without paying full E2E costs [R3]. Many senior teams weight their suites toward this layer.

The two classic shapes

1. Database-backed tests

test "saves an order and finds it again":
    db = start_test_database()          # real DB — container or embedded
    repo = OrderRepository(db)
    repo.save(order)                    # Act 1
    loaded = repo.find(order.id)        # Act 2
    assert loaded.status == "pending"
  • Use the real engine when you can. An in-memory fake can't reveal that your SQL uses a Postgres-only feature. Containers (Docker) made spinning up a real database per test run cheap [R2].
  • Fakes are acceptable when the real thing is too heavy and you own the abstraction — but you inherit the risk of drift from reality.
  • Determinism discipline: seed known data, reset state between tests (transaction rollback or re-seeding), never let tests depend on execution order.

2. API-level tests

test "POST /orders returns 201 and persists":
    app = start_application(test_config)
    response = http_post(app, "/orders", payload=valid_order_json)

    assert response.status == 201
    assert db_has_order(id=response.body.id)

This drives a real HTTP request through routing, validation, handlers, persistence — the whole request path minus the network itself. Assert on what a client observes: status codes and response bodies. This shape is the workhorse of backend teams.

The trade-offs you accept

CostMitigation
Slower (seconds, not milliseconds)Keep counts moderate; run in parallel with isolated databases
More setup/teardown machineryInvest in fixtures/helpers once; reuse everywhere
Flakiness riskNo sleeps, no ordering assumptions, fresh state per test

Notice what's not on the cost list: "uncertainty about what to assert." That stays exactly as it was in Lessons 1–2 — observable outcomes through public surfaces. Only the scope widened.
