Software Testing · Lesson 9 of 9

Tests for Customer-Facing Products

≈10 minutes · Prerequisites: L1–L8 · Next: applied capstone

Everything so far happens before release. But customers don't use your test suite — they use production, where reality exceeds anything CI simulated: real traffic patterns, real data shapes, real third-party outages. Mature organizations extend the testing philosophy past the deploy button.

The pipeline as a series of gates

commit → unit tests        (seconds — reject fast)
      → integration tests  (minutes — verify seams)
      → E2E smoke          (critical journeys only)
      → staged rollout     (canary → percentage → full)

Each gate is Lesson 1's cost-of-defect table operationalized: catch it as cheaply as possible, escalate what escapes. Two properties matter more than any tooling:

  • Red means stop. A gate everyone bypasses is decoration. The suite's authority comes from the discipline to block merges [R4].
  • Fast gates first. Ordering by speed keeps feedback cheap — the pyramid's logic applied to time.

Canary releases: the experiment becomes the test

Instead of betting the whole customer base on one deploy, ship to 1–5% of traffic first. Production telemetry — error rates, latency, conversion — now acts as a test with real inputs at real scale. If the canary's metrics deviate, roll back; blast radius was one-twentieth of your users, not all of them [R6].

Feature flags: decoupling deploy from release

A flag lets broken-but-deployed code stay dark until toggled. This transforms incident response from "roll back the deployment" (slow, risky) into "flip the flag off" (seconds). It also enables testing in production deliberately: enable for internal users, then beta cohort, then everyone.

Error budgets: reliability as a number

If you promise 99.9% availability, your error budget is 0.1% — roughly 43 minutes of downtime per month. Spend it fixing things; exceed it, and new feature launches freeze until reliability recovers.— the Google SRE model [R6]
The deep insight: error budgets turn the age-old fight between "ship features" and "stay reliable" into arithmetic. Reliability stops being a vibe and becomes a budget line — which is exactly how testing stopped being a vibe back in Lesson 1.

Observability: the always-running test

Pre-production testProduction counterpart
Unit/integration assertsAlerts on metric thresholds (error rate, latency)
E2E journey testsSynthetic monitors replaying critical journeys continuously
Test failure reportDashboards + traces localizing which service degraded

Synthetic monitors are worth naming: scripts that log in and click through checkout every few minutes from outside your network. They're E2E tests running permanently — often catching certificate expiries, DNS breakage, and regional outages nothing in CI could see.
