Applied Capstone: Audit & Extend a Real Suite

≈45–60 minutes of hands-on work · Target: this repository (AgentNexus) · Coaching: ask me anything mid-work

Nine lessons of theory, perfect scores throughout. Now the only exam that matters: unfamiliar-enough real code, judged and extended by you. This capstone has three parts. Do them in order; bring results back to me for review after each.

Part 1 — The Five-Minute Suite Audit (L6)

Run each check yourself, in order, and write down what you find:

#CheckHow
1Count tests per layerCount files under tests/unit/, tests/integration/, tests/e2e/; then run uv run pytest --collect-only -q and compare totals per directory
2Does mass match risk?Pick the two most business-critical modules you know in src/ — do their layers dominate the counts?
3Failure localizationOpen three failing-looking candidates: would a failure there point precisely at behavior, or vaguely at choreography?
4Anti-pattern scan (L8)Grep the suite for sleep(, bare assert True-style weak asserts, auto-retry wrappers, and fixtures defined far from use (mystery guest)
5Run the suiteuv run pytest tests/unit -x -q — note wall time. Then integration. Would anyone wait for full green before merging?
Deliverable 1: a five-line verdict — what shape is this suite, where does its mass sit relative to risk, and which anti-patterns did you spot? Bring it to me; I'll pressure-test it like a senior reviewing your PR description.

Part 2 — Read Before Writing (L2, L4)

Before writing anything, read these existing tests closely — they show this repo's conventions:

  • tests/unit/test_circuit_breaker.py — unit-layer example
  • tests/integration/test_health.py — API-level integration example
  • tests/conftest.py — shared fixtures (note what's visible vs hidden from each test)

While reading, judge: are names behavior-style? Is AAA legible top-to-bottom? Any doubles on in-process collaborators?

Part 3 — Write Two Tests (the real exam)

In src/, pick ONE module that currently lacks direct coverage. Then:

3a. One unit test

  • Targets one observable behavior through the smallest public surface — no private reach-ins
  • Strict AAA, exactly one Act, self-explaining assert messages
  • Name: test_<behavior>_when_<condition>.py-style claim
  • Doubles only for out-of-process dependencies — prefer stubs/fakes over mocks [L3]

3b. One integration test

  • Crosses a real boundary (API endpoint → handler → persistence) following test_health.py's pattern
  • Asserts on status codes / response bodies / persisted state — never internals [L4]
  • Deterministic: seeded data, no ordering assumptions, no sleeps

Verify both: uv run pytest path/to/your/tests -v — then deliberately break the source code they guard and watch them fail. A test you've never seen fail proves nothing.

The trap to avoid: don't chase coverage numbers here. One sharp behavioral test beats ten hollow ones — Lesson 7's economics apply to your own PR most of all.
Deliverable 2: open the two test files with me. I'll review them against every rubric from Lessons 2–8: scope, shape, naming, doubles discipline, determinism, diagnosability.

Why this works

This is desirable difficulty by design: retrieval (audit from memory), transfer (theory → unfamiliar code), and production pressure (tests must actually run and actually catch breakage). Fluency got you perfect scores; this builds storage strength.

I'm your pair-programmer for this. Stuck choosing a module? Unsure whether something deserves a stub or a fake? Found something weird in the audit? Bring it to me immediately — that conversation IS the lesson.
