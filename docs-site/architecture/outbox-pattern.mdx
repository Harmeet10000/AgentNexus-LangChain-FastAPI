## The dual-write problem

Any handler that commits a database change *and* publishes an event performs two writes to two systems. Between them lies a window where reality disagrees with itself:

- Commit succeeds, publish fails → the world never learns the thing happened.
- Publish succeeds, commit fails → the world reacts to something that never happened.

Retries make it worse, not better. The outbox pattern removes the window instead of managing it.

## The solution

Write the event **in the same transaction** as the state change it describes. Either both happen or neither does. The `with_outbox()` helper (`src/app/shared/outbox/helper.py`) does exactly that:

```python
event_id = await with_outbox(
    session,
    aggregate_type="document",
    aggregate_id=document_id,
    event_type="document.ingested",
    payload={"doc_id": document_id},
)
```

It inserts into `outbox_events` and calls `pg_notify('outbox_channel', event_id)` inside the same transaction. Because PostgreSQL notifications are transactional, delivery happens only after commit — the notification can never announce an uncommitted event.

## The relay

`OutboxRelay` (`relay.py`) runs alongside the app:

1. **Startup scan** — on boot, publish every row where `published_at IS NULL` (covers events whose notification fired while nobody listened).
2. **LISTEN loop** — wait on `outbox_channel`; each notification triggers publication of that event.
3. **Publish & mark** — dispatch the event as a Celery task through `CeleryTaskRegistry.typed_send(event_type, kwargs=payload)`, then set `published_at`.
4. **Failure accounting** — increment `publish_attempts`, record `last_error`. After **5 failed attempts** (`_MAX_RETRIES` in `relay.py`), the row moves to `dead_letter_events` with its error preserved.

The hot query — unpublished events in arrival order — has a dedicated partial index `idx_outbox_unpublished ... WHERE published_at IS NULL`, declared both in migration and model so they cannot drift.

## Schema

`outbox_events`: `id (uuid)`, `aggregate_type`, `aggregate_id`, `event_type`, `payload (JSONB)`, `created_at`, `published_at?`, `publish_attempts`, `last_error?`.

`dead_letter_events`: same shape plus `original_event_id` and `dead_letter_at`. Dead-lettered events are *parked*, not deleted — inspect them with SQL and re-drive manually once the root cause is fixed.

## Operating notes

- At-least-once delivery means consumers must be idempotent. Task-level deduplication uses Redis idempotency keys with `CELERY_IDEMPOTENCY_TTL_SECONDS = 86400`.
- The relay is part of durability, not a message broker replacement: it guarantees committed state changes eventually produce their events.
- Replay tooling: `uv run replay-outbox` re-drives unpublished/dead-lettered rows after fixing an outage.
