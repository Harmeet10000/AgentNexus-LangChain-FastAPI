## The dual-write problem

Any handler that commits a database change *and* publishes an event performs two writes to two systems. Between them lies a window where reality disagrees with itself:

- Commit succeeds, publish fails → the world never learns the thing happened.
- Publish succeeds, commit fails → the world reacts to something that never happened.

Retries make it worse, not better. The outbox pattern removes the window instead of managing it.

## The solution

Write the event **in the same transaction** as the state change it describes. Either both happen or neither does. `PostgresOutboxAdapter` (`src/app/events/writer.py`) does exactly that through the caller-owned `JobBus` transaction seam:

```python
job = prepare_job("tasks.documents_ingest", payload)
event_id = await job_bus.in_transaction(session).enqueue(
    job,
    aggregate=AggregateRef(aggregate_type="document", aggregate_id=document_id),
)
```

It inserts into `outbox_events` and calls `pg_notify('outbox_channel', event_id)` inside the same transaction. Because PostgreSQL notifications are transactional, delivery happens only after commit — the notification can never announce an uncommitted event.

## The relay

`OutboxRelay` (`relay.py`) runs alongside the app:

1. **Startup scan** — on boot, publish at most the 100 oldest rows where `published_at IS NULL` and `publish_attempts < 5` (covers part of the backlog whose notification fired while nobody listened).
2. **LISTEN loop** — wait on `outbox_channel`; each notification triggers publication of that event.
3. **Publish & mark** — dispatch the validated event as a Celery task through the direct publication adapter, then set `published_at` only after receiving a `DirectEnqueueReceipt` task ID.
4. **Failure accounting** — increment `publish_attempts` and record `last_error`. After **5 failed relay publication attempts** (`_MAX_RETRIES` in `relay.py`), the row is copied to `dead_letter_events` and removed from `outbox_events` with its error preserved.

The startup scan is a single bounded batch, not a full-backlog drain. The live listener handles notifications received after it subscribes, but PostgreSQL notifications are not a durable queue while the relay is offline. Monitor the count and age of unpublished `outbox_events`; if more than 100 rows remain after startup, a subsequent controlled relay restart runs another 100-row scan. Repeat controlled restarts until the backlog is drained before declaring recovery complete. `uv run replay-outbox` replays only rows already in `dead_letter_events`, not arbitrary unpublished rows.

The hot query — unpublished events in arrival order — has a dedicated partial index `idx_outbox_unpublished ... WHERE published_at IS NULL`, declared both in migration and model so they cannot drift.

## Schema

`outbox_events`: `id (uuid)`, `aggregate_type`, `aggregate_id`, `event_type`, `payload (JSONB)`, `created_at`, `published_at?`, `publish_attempts`, `last_error?`.

`dead_letter_events`: same shape plus `original_event_id` and `dead_letter_at`. Dead-lettered events are *parked*, not deleted — inspect them with SQL and re-drive manually once the root cause is fixed.

## Operating notes

- At-least-once delivery means consumers must be idempotent. Task-level deduplication uses Redis idempotency keys with `CELERY_IDEMPOTENCY_TTL_SECONDS = 86400`.
- The relay is part of durability, not a message broker replacement: it stages committed events for publication, but the bounded startup scan and notification gap require backlog monitoring and operator recovery.
- Replay tooling: `uv run replay-outbox` re-drives rows already in `dead_letter_events` after fixing an outage; it does not drain arbitrary unpublished rows.

## Current migration state

The modern producer interface is `JobBus`. Existing auth and document feature callers may still import `events.with_outbox`; that compatibility facade prepares the raw name and payload through the same immutable catalog and `PostgresOutboxAdapter`. New producer code should use the typed `JobBus` transaction seam, while compatibility callers remain valid during migration.
