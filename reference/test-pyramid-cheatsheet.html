The Test Pyramid, On One Page

After Ham Vocke, The Practical Test Pyramid (martinfowler.com). Print-friendly.

E2E — few · critical journeys only
Integration — some · real boundaries
Unit — many · fast behavior checks

Decision map: which kind, where

Question about the codeTest kind
Pure logic: calculations, parsing, state rules, validationUnit
Does my code talk to the database/queue/API correctly?Integration
Do the pieces compose into a working request flow?Integration (API-level)
Can a user actually sign up, buy, reset their password?E2E
"Does it boot and serve at all?" after each deploySmoke

Rough proportions

  • Unit: the bulk — hundreds. Each runs in milliseconds.
  • Integration: dozens–hundreds. Seconds each; still run on every commit.
  • E2E: a handful — one per money-critical or mission-critical journey.

Do NOT test

  • Trivial code: one-line getters, constants, pure delegation with no logic
  • Third-party library internals — test your usage of them instead
  • Generated code and configuration files
  • Private implementation details of well-tested public behavior

A good test is…

TraitTest
FastYou'll run it thousands of times; slowness compounds.
DeterministicSame input → same result, every run. No sleeps, no random.
IndependentPasses alone and in any order; shares no mutable state.
Behavior-focusedAsserts observable outcomes, not internal call sequences.

Source: Vocke, The Practical Test Pyramid; see also Khorikov, Unit Testing (Manning) ch. 1–2.
