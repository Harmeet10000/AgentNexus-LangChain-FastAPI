Software Testing Glossary

Canonical vocabulary used across every lesson in this course. Print it, keep it beside you.

Test kinds

TermMeaning
Unit testVerifies one small piece of behavior (a function, a class) in isolation from slow collaborators like databases or networks. Fast enough to run constantly.
Integration testVerifies that several components work together — especially across a real boundary: database, message queue, file system, another service.
End-to-end (E2E) testDrives the whole deployed system the way a user would — through the UI or public API — verifying a complete user journey. Slowest, fewest.
Smoke testA minimal sanity check that the system basically works ("does it boot and serve?") before deeper tests run. Often the first gate in deployment.
Contract testVerifies two services agree on the shape of their communication (request/response schema) without needing to run both live.

Anatomy & structure

TermMeaning
SUT"System Under Test" — the specific thing being verified by a given test. Everything else is either a collaborator or scaffolding.
AAAArrange–Act–Assert: set up inputs, do the one action, check the outcome. The standard three-beat shape of every good test.
FixtureThe known, fixed context a test needs: data, files, configured objects. Good frameworks let fixtures be shared without copy-paste.
AssertionThe single statement that checks reality against expectation. A test with weak assertions can't fail when it should — a silent danger.

Test doubles

A test double is any object standing in for a real dependency during a test (the movie-stunt-double metaphor).

DoubleWhat it does
DummyFills a parameter slot; never actually used.
StubReturns canned answers to calls — you don't care how it was used, only what comes back.
SpyA stub that also records how it was called, so assertions can inspect the record later.
MockPre-programmed with expectations: the test fails if the expected calls don't happen exactly. Overuse creates brittle tests.
FakeA working lightweight implementation (e.g., in-memory database). Preferred over mocks for stateful dependencies.

Strategy & health

TermMeaning
Test pyramidFowler/Vocke's model: many unit tests at the base, fewer integration tests in the middle, few E2E tests at the top (cheat sheet).
Testing trophyKent C. Dodds' counter-model: integration tests are the biggest, most valuable layer; static analysis below, unit and E2E smaller.
Flaky testA test that passes and fails on identical code — usually timing, ordering, or shared-state bugs. Flakiness destroys trust in the whole suite.
RegressionPreviously-working behavior broken by a change. The suite's core job is preventing regressions.
Code coverage% of code executed by tests. Necessary but insufficient — high coverage with weak assertions proves nothing.
CI (Continuous Integration)Every change automatically builds and runs the suite on a shared server; red build = change doesn't merge.
Canary releaseShipping a change to a small slice of real users first; production telemetry acts as the final test layer.

Process terms

TermMeaning
TDDTest-Driven Development: write the failing test first, then make it pass, then refactor. Red → green → refactor.
BDDBehavior-Driven Development: express tests as user-visible behaviors ("given/when/then") to bridge business and engineering language.
Exploratory testingSkilled, unscripted investigation of a running system — humans finding what scripts didn't think to ask.
